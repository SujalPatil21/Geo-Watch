1. What is GeoWatch?

The Core Problem

During crowded events, emergency reports come from all over the area. Organizers get overwhelmed and cannot easily spot the actual danger zones amidst isolated or false alarms.

We need to answer: "Where are incidents clustering together right now, and which zones are becoming safety hazards?"

The Platform's Solution

GeoWatch acts as a live coordinator:

Collects GPS incidents → Finds nearby groups → Identifies risk zones → Updates a live map

30-Second Interview Answer

"GeoWatch is a real-time safety dashboard. It ingests geo-tagged incident reports from mobile users, runs validation and rate limiting on the backend, and groups them into risk hotspots using an optimized clustering algorithm. It then broadcasts these hotspots instantly over WebSockets to a live map interface for event organizers."

The Core Concept in Simple Steps:

  • Ingestion: A user reports a safety concern. The backend validates if the report falls inside the event boundaries (geofencing) and rate-limits spam.
  • Clustering: The server retrieves active incidents from the last 15 minutes, runs them through the DBSCAN algorithm, and determines risk levels (Low, Medium, High).
  • Push: The server broadcasts the resulting cluster coordinates instantly over WebSockets. The dashboard receives it and re-renders hazard visual shapes.

4. Backend Code Structure

Standard Layered Architecture

We separate concerns into logical layers:

Controller → Service → Repository → Entity

  • Controller (IncidentController): The entry gate. Receives the incoming request, triggers checks, and sends back the incident ID.
  • Service (IncidentService): The logic brain. Handles event timings, geofencing, rate limiting, and triggers DBSCAN.
  • Repository (IncidentRepository): Database messenger. Asks PostgreSQL for matching incidents.
  • Entity (Incident): Defines how an incident is structured inside the database.

DTOs (Data Transfer Objects)

DTOs carry data across the API separately from the database tables. This isolates client requests from database schema modifications.

  • Client sending a report:
    JSON HTTP Payload → DTO (CreateIncidentRequest) → Service → Entity → DB
  • Server sending cluster information:
    Service Runs DBSCAN → DTO (ClusterResponse) → JSON Broadcast

5. DBSCAN Clustering: Concepts & Parameters

What is DBSCAN?

DBSCAN is a spatial algorithm that groups points close to each other. It finds natural clusters of any shape and ignores isolated points as random noise.

  • 10 reports close together: Forms a hotspot cluster (Risk Zone).
  • 1 isolated report: Treated as noise and does not trigger an alarm.
  • Why it fits: We do not need to guess the number of clusters beforehand.

Parameters and Code Settings

The code (DbscanClusteringService.java) defines two thresholds:

  • Epsilon (EPS = 50.0): 50 meters. The maximum distance between two incidents to count them as neighbors.
  • MinPoints (MIN_PTS = 2): At least 2 incidents must be close to form a cluster. If fewer, they are treated as noise.

6. Spatial Optimization: The Grid Index

The Performance Bottleneck

Normally, finding neighbors requires comparing every incident with all other incidents on the map. This represents $O(N^2)$ complexity which slows down exponentially during heavy reporting load.

Our Solution: 2D Spatial Grid

We divide the map into 50m cells. Each incident is assigned to its cell. When searching for neighbors, we check only the host cell and its 8 adjacent cells (3x3 grid) rather than the whole database. This yields $O(N)$ efficiency.

0.92 ms: The measured DBSCAN execution time on active in-memory incidents in our benchmarks.

7. Real-Time WebSockets & Broadcasting

Why WebSockets over Polling?

REST Polling: The browser repeatedly asks "Any updates?" every few seconds, wasting battery, database connections, and server bandwidth.

WebSockets: Establish a single, persistent two-way channel. The server pushes updates to the dashboard only when data actually changes.

STOMP Channels & Concurrency

STOMP organizes WebSocket streams into channels. The server broadcasts cluster updates to the topic /topic/risk-updates/{eventId}.

  • 500+ Concurrent Clients: The backend successfully handles 500+ long-lived connections open simultaneously in JVM memory.

10. Rapid-Fire Interview QA

1. Why DBSCAN? It groups points by proximity, identifies clusters without a predefined count, and ignores isolated points as noise.
2. Why not K-Means? K-Means requires specifying cluster counts upfront, handles outliers poorly, and assumes spherical groups.
3. What is the grid index? It divides the map into cells so DBSCAN only queries adjacent cells instead of comparing all incidents.
4. Explain the 0.92 ms speed. It is the in-memory execution speed of DBSCAN algorithm over incidents, excluding database and network transport time.
5. Entity vs DTO? Entities map directly to relational tables. DTOs carry data across the API, decoupling client requests from table schemas.
6. Controller vs Service vs Repository? Controller ingests requests. Service coordinates business and validation logic. Repository executes database transactions.
7. Why PostgreSQL? It is reliable, relational, and supports composite indexing on event metadata and phone numbers to keep queries fast.
8. Why WebSockets instead of polling? WebSockets hold a persistent connection to push data immediately, avoiding the network overhead of periodic HTTP polling.
9. What is STOMP? A simple messaging protocol running over WebSockets that structures data frames into subscribe/publish topics.
10. What was the main technical challenge? High concurrent database writes. Resolved by implementing a 100ms background debounce scheduler to throttle DBSCAN calculations.
